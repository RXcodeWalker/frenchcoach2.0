# CLAUDE.md

Guidance for Claude Code working in this repository. Keep this file lean — if something can be discovered from the code or from `docs/`, it doesn't belong here.

## What This Is

A French speaking-practice app for IGCSE/A-Level learners (Vite + React + TypeScript frontend, localStorage-first state). Users record spoken French, get AI feedback, earn XP, and track skill mastery. The project is mid-rewrite of its **Cambridge IGCSE French (0520) speaking scorer** — the "Assessment Engine" — replacing older ad hoc scoring logic with a single audited, three-layer pipeline.

## Three Runtime Surfaces — Don't Conflate Them

1. **`src/`** (this repo) — the React frontend.
2. **`server/`** (this repo, separate deploy) — a Node service that hosts the **Cambridge scoring API**. It imports `scoreAttempt` from `scripts/scoring/scoreAttempt.ts` directly. It also hosts `POST`/`GET /feedback`, the post-marking exam report (`server/feedbackRoute.ts`), which reads a persisted envelope and never changes a mark. Deployed per `render.yaml` (`french-scoring` service).
3. **`backend/`** — a **separate git repository** (own remote, own `.gitignore`, listed in this repo's root `.gitignore`) running FastAPI. It handles general coaching feedback, transcription, and exam endpoints — **not** Cambridge scoring. Before editing it, run `git -C backend status` (expect clean) and `git -C backend push` after committing there; this repo's history is no safety net for `backend/` changes. Vercel proxies `/api/*` to the deployed FastAPI service (see `vercel.json`); the scoring service is a separate Render host.

`backend/evaluator_service.py` *does* contain a second, unsourced Python rubric — it is legacy and unreached from `src/` (zero callers), not a design intent. See `docs/decisions/0003-node-engine-is-the-authoritative-scorer.md` for the evidence; don't "fix" its rubric to match `rubric.ts`, that's out of scope for any documentation or normal feature change.

Full topology (deploy wiring, env vars, known unknowns): `docs/systems/topology.md`.

## Core Architectural Rules

1. **Cambridge IGCSE French (0520) only.** No generic rubric engine, no `ExamBoard` abstraction, no multi-board future-proofing. This is referenced in code as "hard-constraint #1" (see `src/domain/igcse/rubric.ts`). See `docs/decisions/0001-cambridge-0520-only.md`.
2. **Three-layer scoring pipeline, never collapsed:** deterministic evidence extraction (`evidence/`) → constrained LLM judgement (`judgement/`) → deterministic guardrails (`guardrails/`) → persisted `ScoringEnvelope` (`envelope/`). Don't replace with pure-deterministic or unrestricted-LLM scoring. See `docs/decisions/0002-three-layer-scoring-pipeline.md` and `docs/systems/assessment-engine.md`.
3. **Every rubric number is sourced.** Mark ranges, band descriptors, and thresholds must trace to official Cambridge documentation — check `src/domain/igcse/rubric.ts`'s own source comments (it cites the specific Teacher/Examiner Notes booklet). Anything uncertain is marked `UNVALIDATED`, not guessed.
4. **All frontend app state flows through `AppContext`'s single reducer** + the three localStorage services. Don't introduce parallel state stores for existing app data.
5. **Calibration and validation datasets stay separate**, and validation-corpus availability is never assumed. Ask before assuming any graded/held-out corpus exists rather than inferring it from code.
6. **Examiner-voice practice feedback (Learn and the Coached rail) never emits a mark, band, or grade.** See `docs/decisions/0005-examiner-feedback-emits-no-marks.md` and `docs/decisions/0009-feedback-after-marking-cannot-change-marks.md`.

## Development Workflow

**Always push after committing — no exceptions, no "I'll push later."** This repo commits straight to `main` (no feature branches). Every `git commit` in this repo is followed by `git push` in the same turn, and every commit made inside `backend/` (its own separate git repository — see **Three Runtime Surfaces**) is followed by `git -C backend push` (or `git push` from within `backend/`) in the same turn. A commit that isn't pushed doesn't count as done.

**General app changes:** inspect the relevant screen/service and its existing contracts → implement the smallest correct change → `npm run typecheck` + `npm test` for touched areas → `npm run lint` → review the diff → **update `CLAUDE.md` in the same session if the change makes a claim in it stale or incomplete**, then update `README.md`/other docs if documented behavior changed.

**Assessment Engine changes** (`src/domain/igcse/`, `server/`, `scripts/scoring/`, `scripts/stt/`): higher-risk than a normal change — see `src/domain/igcse/CLAUDE.md` and `docs/guides/development.md`'s Assessment-Engine change procedure before touching `evidence/`, `judgement/`, `guardrails/`, `envelope/`, or `rubric.ts`.

Full command list, the three test suites, and what each command does/doesn't cover: `docs/guides/development.md`.

## Keeping This File Current

`CLAUDE.md` is only useful if it matches the repo. **Before ending any implementation task, check whether it made one of these true, and if so, edit the relevant section in the same session — don't defer it:**

- A new runtime surface, or a change to how the three existing ones relate → update **Three Runtime Surfaces** and `docs/systems/topology.md`.
- A new invariant you had to introduce or enforce (a new "don't do X" you'd want the next session to know) → add it to **Core Architectural Rules** or **Known Traps**, not just the commit message.
- A doc `CLAUDE.md` points to (in **Source of Truth** or **Documentation map**) is added, moved, or deleted → update the pointer.
- A canonical-implementation claim in **Known Traps** turns out to be wrong (you find a second XP formula, a "dead code" path that's now wired up, etc.) → correct it, don't leave it for a future audit.
- A `docs/` move or reorganization → update **Documentation map** to match.

If none of these apply, don't touch `CLAUDE.md` — a diff here on every change is as bad as a stale file. When in doubt about whether something is "almost every session" material versus a one-off detail, leave it out; over-including degrades the file faster than under-including does.

## Known Traps

- **"Feedback restructure" (Phase 2.5) was never implemented.** No flag, no code. If older docs or discussion reference it, treat that as describing work that doesn't exist in this codebase.
- **Don't confuse `backend/data/igcse/*.json` (question-bank content) with `src/domain/igcse/` (scoring engine code).** The former is validated by `npm run authoring:check`; the latter is the actual rubric/evidence/judgement/guardrail pipeline and lives in this repo, not `backend/`.
- **Question-bank rules come in two tiers, and a pattern rule never moves into `validate.ts`.** `src/data/exam/bank/validate.ts` errors are runtime-fatal (the loader and `server/resolveQuestionSet.ts` fall back to the fixture), so only rules the Teacher's Notes or syllabus *state* live there: `topic-area-slot` (topic 1 from A/B, topic 2 from C/D/E), the closed Syl p.14 `subTopic` enum (`sub-topic-not-in-area`), `alternative-on-q1-q2`, `roleplay-alternative` — mirrored in `backend/models/igcse.py`. Script *patterns* (two-part positions, 2–3 two-part role-play tasks, past + future/conditional in Q3–Q5, echo-choice, trivial closings, loaded negatives) are authoring-only in `patternLint.ts`, run only by `npm run authoring:check` (D12). The backend JSON is canonical: `src/data/exam/bank/fixtures/` is generated by `npm run authoring:generate` and checked by `npm run authoring:parity` — never hand-edit a fixture. `alternativeTexts` is the alternative question's ordered parts (D9), and `AuthoredTopic.title`/`rolePlay.examinerRegister` are unhashed, like `setup`.
- **The canonical XP formula is `src/domain/xp.ts`'s `computeXPGain`**, not `progressionService.ts` (which calls it). Similarly, the canonical color-to-score mapping is `src/domain/scoring.ts`. Both have been duplicated informally elsewhere in the past — if you find a second implementation, that's drift, not a second source of truth.
- **`all_time_leaderboard` is ledger-backed (`profiles.xp_baseline + SUM(xp_events.amount)`).** `profiles.total_xp` is no longer client-writable (removed from the `authenticated` UPDATE grant, Phase 1.3) and is no longer authoritative for the all-time board. `profiles.achievements` is still client-writable — a known accepted risk until server-side achievement derivation exists (`recompute_achievements` currently has zero firing predicates).
- **`src/services/supabase/` is not dead code.** Auth, sync, social, shop, league, and duel features are all wired through Supabase — check for existing usage before assuming a feature needs new plumbing.
- **Only the Node engine scores Cambridge attempts.** `backend/evaluator_service.py` is a legacy, unreached second scorer; the third (`/api/feedback/igcse`) was deleted in Phase 3 Batch C. See `docs/decisions/0003-node-engine-is-the-authoritative-scorer.md`.
- **`useRecording`'s callbacks are generation-guarded.** `start()` increments a `generationRef` counter each call and every callback bound during that call (`onresult`/`onend`/`onerror`/`ondataavailable`/`onstop`) checks it's still the current generation before touching shared state (`finalTextRef`, `chunksRef`, `resolveRef`, `blobResolveRef`). Never assume the most recently fired callback belongs to the most recently started recording — `SpeedSpeaking.tsx`/`SpeakingArena.tsx` call `stop()` without awaiting it before the next `start()`, so a stale recognizer's `onend` can arrive after a new recording has already begun; the guard (not call-site awaiting) is what keeps that safe.
- **Every AI endpoint is behind `verify_jwt` (Phase 3), but guests are TEMPORARILY let through (`guestAiEnabled()` in `src/lib/authToken.ts`, default on; `GUEST_AI_ENABLED` on the backend, default on, `backend/lib/guest.py`).** A header-less request is accepted as `guest:<ip>` and counted against caps instead of the Supabase quota/invite RPC: the client gives a guest 3 free feedback attempts (`checkGuestAttempt`, localStorage, same question+transcript counted once) then throws `AuthRequiredError` (sign-in prompt); the backend adds a looser per-IP lifetime-of-process backstop (`GUEST_AI_LIMIT`/`GUEST_AI_AUDIO_LIMIT`, in-memory, resets on restart, spoofable IP); a *present* bad token still 401s. Guests get no pronunciation coaching. To go back to sign-in-only, set `VITE_GUEST_AI_ENABLED=0` at build **and** `GUEST_AI_ENABLED=0` on the backend; everything below then applies again. With guests off, a guest has no Supabase session, so any AI call they make can only return 401 — `src/lib/authToken.ts` is the single place that resolves (and near-expiry-refreshes) the token, and `AuthRequiredError` is what a call site raises *instead of* firing the request. New calls to an auth-gated backend route go through `requireAuthHeader()`/`getAccessToken()`, never a bare `getSession()`; a route that is NOT gated (currently only `/api/generate-scenario`) uses the optional header so guests keep working. Signed out, Learn falls back to offline evaluation with `failoverReason === SIGNED_OUT_FEEDBACK_REASON` and pronunciation reports `signed-out`, both surfacing a sign-in prompt rather than "you're offline"/"try again".
- **Judge model IDs (`geminiJudge.ts`/`groqJudge.ts`) are always env-driven (`GEMINI_MODEL`/`GROQ_MODEL`), never a bare literal** — same convention as the backend, where every Groq/Gemini caller imports its model ID from `backend/lib/model_config.py` (a module-local fallback default once drifted to a retired model and 404'd `/api/exam/interpret` on every call — never add one). A hardcoded model ID that becomes deprecated has no way to be swapped without a redeploy; if you add a new judge provider or another Gemini/Groq call site, read the model from the matching env var with a literal only as the fallback default, and verify that fallback is still a live model ID before trusting it.
- **Under-13 accounts require guardian confirmation before any audio capture / provider call.** The gate is `profiles.consent_status` (never client-writable) + `SpeakingConsentGate` wrapping the record control, backed by a `useRecording(blocked)` guard. Browser mic permission is never treated as consent — see `docs/systems/child-safety-consent.md` and ADR 0006. `SpeakingConsentGate`/the `blocked` guard are wired into Learn, ExamMode, RoleplaySession, StoryMode, ScenarioArchitectSession, DailyNewsFlash, and `OnboardingPlacement` (the post-onboarding placement diagnostic) — **not** into `useAudioBlobRecorder` (`SayItAgainCard.tsx`'s practice-step recorder) or SpeakingArena/SpeedSpeaking. That's a known gap, not a design decision. The backend now also refuses the audio itself: `backend/lib/consent.py` answers `/api/pronunciation` and `/api/transcribe` with 403 `{"error":"consent_required"}` for a signed-in `pending` account (or one with no profile row; an unreadable status is a 503; guests are not gated), and the client maps that to `ConsentRequiredError` (`src/lib/consentRequired.ts`) → `GuardianConsentNotice`, never to "sign in again". So Say-It-Again/Accent Analyzer/Shadowing still *record* for a pending account, but their upload never reaches a provider.
- **The Learn adaptive-difficulty engine (`src/domain/learn/`) is live, not bypassed, and now covers all 668 questions** (Batch 3b tagged the last 240; 660 core-topic tags are a model re-read still marked `inferred` at confidence 0.8, 8 are human-`reviewed`). `src/data/questions.ts` hydrates each `Question.demands` from the generated `src/data/learn/demandsManifest.ts` at module load; `deriveAbility`/`selectQuestions` branch on `question.demands` presence, so cold-start (`abilityScore = 4.5`) only applies until real evidence accumulates. A new post-onboarding placement diagnostic (`OnboardingPlacement.tsx`, route `/onboarding/placement`) seeds `frenchCoach_aim` from 5 scored questions instead of leaving it at the cold-start default; skipping the diagnostic (or leaving it incomplete) is a supported path and leaves `aim` untouched. Advanced Learn topics are now really gated (`src/features/learn/topicProgress.ts` + `src/data/learnTopicDependencies.ts`), not just a "continue anyway" warning modal. **Aim and the cold-start tier come from `AppState` via the caller** (`buildSessionQuestions(…, { aim, migratedTier })`, `sessionAbility()`), never from `storageGet(difficulty)` — `SET_DIFFICULTY` writes the tier raw, so a JSON read is always null (that bug kept every learner on `balanced` + the 4.5 seed until Batch 1). The tier no longer shapes anything else: Learn's avoidance uses the fixed `IGCSE_EXPECTATIONS`, and the tier grid is gone. Only 8 of 668 tags are human-reviewed (the owner's `reviewed` flip is what lifts a tag's weight from ≈0.26 to ≈0.41 — see `adaptiveSimulation.test.ts` scenario M), so stretch slots are rare and the level read-out stays a "starting point" (`levelLabel()`: Warm-up (A1) / Exam level (A2) / Stretch (B1) / Stretch (B1+), never B2/C1); a downgraded stretch uses the target band, and "Why this question?" comes from slot + rung + real level (`explainSelection`). An Examiner-voice Learn answer records L1 demand evidence only (`recordDemandOnlyAttempt`) — never route it through `orchestrateAttempt` (no Session, XP, mastery or review write). Topic `averageScore` is `number | null` — never write a fabricated 0 (`features/learn/topicAverage.ts`). **Learn setup filters (Batch 2, docs §8.5)** go through ONE pool: `topicPool(topicKey, filters)` feeds slotting, the review slot (`getEligibleReviewQuestion`'s `accept`) and `midSessionAdjust` — never hand `midSessionAdjust` or the builder the unfiltered `getTopicQuestions`, and never pad a filtered session with non-matching questions; follow-ups are off while a grammar filter is on. The learner does not pick an AI engine (the stored `preferredEngine` is used), and topics under 5 questions are hidden from the grid. Sessions are routinely shorter than the length tapped (unfilled review slots are not backfilled, §8.3) — don't treat that as a filter bug.
- **The Learn spaced-review pool (`src/services/coach/reviewPool.ts`) is real SM-2, not a flat cooldown.** `recordReviewOutcome` (Phase 4.2) fires on every scored answer — pass or fail — via `sessionOrchestrator.ts`'s step 9; a `review` slot now means "due for spaced repetition," not "you got this wrong." An item graduates (is deleted) once a passing round pushes `intervalDays` past 30; re-encountering that question later via ordinary selection starts a brand-new SM-2 item from scratch, never a resumed schedule. **`getEligibleReviewQuestion` must be passed only this session's picks**, never the historical seen set — every review item was answered before, so excluding `seen` silently stopped review from ever firing (fixed in Batch 1; tests with a realistic `topicMastery` in `sessionBuilder.reviewExclusion.test.ts`).
- **Notifications (streak-at-risk / daily-goal) run over Web Push + email, hourly, from `.github/workflows/notifications-streak-and-goal.yml`.** This is the first GitHub Actions workflow that makes outbound HTTP calls (Web Push via `web-push`, email fallback via Resend) rather than a single Supabase RPC call — see `docs/systems/topology.md`'s CI section and `scripts/scheduledJobs/sendNotifications.ts`'s header for the claim-before-send (at-most-once-attempt, not exactly-once-delivery) design. `profiles.daily_goal`/`notify_streak`/`notify_daily_goal` are push-only from the client (`profileSettingsSync.ts`) — never pulled back, same one-directional precedent as `streak_days`. The real streak *count* is still never synced server-side (only the fact that a session happened, via `sessions`), so the streak-at-risk copy is necessarily generic ("don't lose your streak"), not "your N-day streak" — a stated, accepted limitation, not a bug.
- **Every Azure Speech call is metered and serialised (exam-pronunciation Batch 1).** It goes through one process-wide `asyncio.Semaphore(AZURE_SPEECH_MAX_CONCURRENCY)` (default 1 — F0 allows one concurrent request) in `backend/services/pronunciation/azure_client.py`, and through a reserve → settle/release row in the `azure_speech_usage` ledger (`backend/lib/azure_budget.py`; seconds measured from the WAV header). The semaphore is only correct while the FastAPI service runs as **one instance with one uvicorn worker** — scaling out needs a cross-process lease instead (`docs/systems/topology.md`). The monthly cap is `azure_speech_budget.cap_seconds`, NULL (unlimited) until the owner sets it; when reached (or Azure itself reports its quota spent) `/api/pronunciation` skips Azure and returns the whisper-heuristic result with `azureBudgetExhausted: true`. A new Azure caller must reserve/settle like `routers/pronunciation.py`'s `_assess_metered`, not call `assess_with_fallback` bare. `/api/repair` (an unauthenticated, unmetered Azure path with no caller) was deleted.
- **Exam pronunciation analysis is feedback-only and invisible to the scorer (exam-pronunciation Batches 4–6; spec `docs/systems/exam-pronunciation.md`, ADR 0010).** Evidence lives in `exam_pronunciation_evidence` (backend `routers/exam_pronunciation.py`, one turn per request, the row is the cache), never in the envelope; nothing under `src/domain/igcse/`, `scripts/scoring/` or `server/` may mention or import it (`dataIsolation`, `scoredPipelineBoundary` tests, an ESLint block) — no exemptions. The route is off unless `EXAM_PRONUNCIATION_ACCESS` is `admin`/`all`; it stays `off`/`admin` until the calibration has passed (it has **not** been run — no corpus, fixtures or probe script exist) **and** the guardian-revocation migration `20261003113100` is applied to production, so a child's evidence can actually be erased; `all` needs both, logged in `verification-log.md`. Fairness thresholds live only in `src/domain/examPronunciation/fairness.ts`'s `FAIRNESS_CONFIG`, hash-pinned by `EXAM_PRONUNCIATION_VERSION` — a threshold change is a version bump; the backend's own logic is versioned by `EXAM_PRONUNCIATION_ASSESSOR_VERSION` (part of the evidence row's unique key). Display types carry no score or accuracy (`types.test.ts`). **The UI (Batch 6)** is `src/features/exam/pronunciation/`: `useExamPronunciation` is owned by `ExamMode` and shared by the report section (`ExamPronunciationSection`, after the marks and the examiner report, never inside either) and, in Coached only, an end-of-part card in the rail (`markPartEnded` from `announceIfPartChanged`/`finishSession` — no engine change). Nothing is analysed until the candidate taps Analyse (the only automatic call is the stored-rows GET on results); recordings stay in `examAudioStore` (browser memory), so a reopened report says "recording not kept". It renders only for an admin or when `VITE_EXAM_PRONUNCIATION_PUBLIC=1` (never for a `pending` account — `access.ts`); the backend's `EXAM_PRONUNCIATION_ACCESS` stays authoritative (403 `not_enabled`). Its e2e runs as a separate Playwright project on its own Vite server, because the admin gate needs a Supabase session and the main e2e server deliberately has none.
- **`backend/lib/ai_quota.py`'s `consume_ai_quota_or_503` requires its `feature` argument to already exist as a row in `ai_quota_limits`** (FK constraint — an unrecognized feature 503s every call, not a graceful no-op) — never assume a plausible-looking feature name (e.g. one matching the endpoint's own name) is provisioned; check the seed migration (`backend/supabase/migrations/20260914090000_invite_gate_and_ai_quota.sql`) first. It's also a *daily* cap shared across every idempotency key for that feature — fine for one call per user action, wrong for a call that fires many times per session (a per-turn exam call reusing the existing `'exam'` row, sized for one submission per attempt, would exhaust it mid-exam). `verify_jwt` and AI-cost quota are separable: `/api/exam/interpret` (W7) is `verify_jwt`-gated but deliberately unmetered — see its own docstring and `verification-log.md`'s W7 entry.
- **Examiner feedback prompts are server-rendered, versioned and metered (Phase 3 Batches 0 and B).** `/api/feedback`'s `feedbackMode:"examiner"` branch 422s a `prompt` field; it takes only `ExaminerFeedbackRequest`'s structured fields (including `inputMode` `speech`|`text`) + `promptVersion`, and 409s a version missing from `backend/data/examiner_feedback/prompts.json` (now `examiner-v3`, whose rail-topic reply adds `strength`, the one best thing, only when there are no mistakes; v2 and v1 are kept for one release; a v2 template declares `responseKeys`, the only top-level keys the backend relays). That file is generated by `npm run examiner:generate` from `examinerFeedback.ts` (CI runs `examiner:parity`), never hand-edited; a new version is a backend commit that must deploy before the frontend sending it, and the pinned hash in `examinerFeedback.test.ts` fails until `EXAMINER_FEEDBACK_PROMPT_VERSION` is bumped with it. Learn charges `feedback`, the Coached rail charges `exam_turn_feedback` (60/day). A quota replay never calls the model: it is served from the cache or answered 409 `already_generated`. The reply is parsed client-side into a union on profile (`learn` / rail `topic` / rail `rolePlay`) through the pure filters in `src/domain/examFeedback/shared/` — deliberately outside `src/domain/igcse/`, and nothing in the scored pipeline may import it (ADR 0009, `scoredPipelineBoundary.test.ts`). A filter drops a claim, never rewrites it; a rail turn with nothing to fix is a valid empty result, not a retry.
- **The post-marking exam report is a separate call that cannot change marks (Phase 3 Batch A, ADR 0009 amendment).** `src/domain/examFeedback/` (outside `src/domain/igcse/`) generates it from an already-persisted envelope via `server/feedbackRoute.ts`, stored in `exam_feedback_reports` (service key only, one row per envelope; a stored report is served with no model call or charge; generation charges `score` with key `feedback:{sessionId}` and a failure releases the grant). Only the named feedback-surface files in `server/` and `scripts/scoring/` (`feedbackRoute.ts`, `supabaseFeedbackStore.ts`, `judgeCheck.ts`, `judgeCheck/feedbackCheck.ts`) may import it, and the scorer's transitive import graph must never reach it (`scoredPipelineBoundary.test.ts`) — never extend a judge prompt or the envelope to carry feedback instead. The report's QoL quote/correction are copied from the envelope (the model only categorises); its prompt is pinned by `EXAM_FEEDBACK_VERSION` + a hash test, independent of every scoring version.
- **Only Exam Sim exam attempts count toward progress.** ADR-0007: Coached Practice (live examiner commentary, typing allowed, transcript editing allowed) still produces a full `/40` `ScoringEnvelope` and report, but `src/services/exam/attemptStatus.ts`'s `countsTowardProgress` decides `Session.practiceOnly`, and every exam-derived aggregate (`roadmapService.ts`'s skill average and IGCSE milestone nodes) must filter on `!session.practiceOnly`. Daily Challenge and Duels are always forced to Exam Sim (`resolveCoachedMode`), never Coached, so compared scores can't come from an easier condition. `ExamSelect`/`ExamMode` default to Exam Sim, not Coached.
- **The conduct engine is mode-aware (`session-engine-v4`).** `initConductEngineState(set, { mode })` takes a `ConductPolicy`, and `step()` needs `clockS` (the session clock) on every candidate turn. Exam Sim gates further questions and the extension cutoff on wall-clock conversation length (the 3½-min further-question floor, the 4-min extension cutoff); Coached has no time-based gating but **always asks both authored further questions per topic** (D5, Batch 3 — not "no further questions": that was an earlier draft, superseded before it shipped). Further questions are authored only (no callbacks quoting the candidate) and have their own engine phase. A two-part question's second part is always asked. An in-role `TRANSITION` now separates answered role-play tasks too (D13, Batch 3), never crossing into topic 1 — the UI speaks its own "role play finished" line there instead. The Teacher's Notes are cited by page only, never quoted — see `docs/systems/exam-conduct-0520.md` and ADR 0008.
- **Exam Sim's 10-minute preparation is a real countdown, not a pacing aid, and a resumed or early-started attempt is practice-only.** `RolePlayCardPreview.tsx` counts down 600s and auto-advances; "Start now" is offered but sets `earlyStart` (`ExamMode.tsx`'s `earlyStartRef`), which `attemptStatus.ts`'s `countsTowardProgress` treats like a typed answer. A mid-exam reload resume is guarded by `localTranscriptStore.ts`'s `RunningSessionSnapshot.questionSetHash`/`engineVersion`: a mismatch (content changed, or an older engine) discards the snapshot instead of resuming into stale state; a matching snapshot IS resumed but marks the attempt practice-only via the `resumed` reason. Both `ExamMode.tsx` and `ExamResults.tsx` need these flags passed explicitly — `ExamResults` recomputes `countsTowardProgress` independently from `coached`+`transcript` for its own banner (so it renders correctly before `ADD_SESSION`'s side effects run), and neither `earlyStart` nor `resumed` is recoverable from the transcript alone.
- **Exam Sim never shows which sets exist, or a role-play/topic's content, before the candidate starts.** `ExamSelect.tsx` renders a single "Start Exam Sim" button (the existing uniform-random pick) in Exam Sim mode — the full catalog (topic areas, sub-topics, role-play titles) only fetches and renders in Coached mode. `DailyChallenge.tsx` (always Exam Sim) no longer previews the assigned set's title or scenario before prep starts.
- **The role-play `setup` is spoken by the UI, never by the conduct engine.** `ExamMode.tsx` has the examiner read `setup` aloud after the greeting and before rp1 (TN p.6 #5), through `speakExaminerText`, so it is not a `ConductLog` entry, not in the scored transcript, and not hashed (`setup` is unhashed by design). Don't move it into `conductEngine.ts`: that would change the log, the transcript projection and `questionSetHash`. The same applies to the topic-title and "role play finished" transition lines.
- **Frontend CI (`.github/workflows/ci.yml`) needs the `backend/` repo.** It checks out the public `RXcodeWalker/french-coach-backend` into `backend/` (same-named branch, else `main`), then runs `typecheck`, `typecheck:server`, `lint`, the full `npm test`, `authoring:check` and `authoring:parity` — tests like `feedbackContractFixtures` read `backend/` files, so the full suite only passes with it present. Locally, `backend/` may be a symlink to the sibling clone (`ln -s ../french-coach-backend backend`, kept out of git via `.git/info/exclude`).
- **Learn's difficulty prompt text is backend-owned; the client sends `{ tier }` and nothing else (Phase 3 Batch F).** `apiClient.ts`'s `buildDifficultyContext` returns `undefined` while `learnAdaptiveDifficulty` is live (the Aim picker hides the tier grid, so the persisted `selectedDifficulty` is invisible to the learner and must not shape the rubric); the backend then injects its default target, "A2 with elements of B1" (TN p.11). The CEFR/tone/rubric sentences live in `backend/main.py`'s `_TIER_PROMPTS`, and an unknown tier or any extra `difficultyContext` key is a 422 — never add a client-supplied sentence back. Changing that prompt text (or `SYSTEM_PROMPT`) is a `LEARN_PROMPT_VERSION` bump plus the hashes in `tests/test_learn_demands.py` (user prompt) and `tests/test_learn_prompt_v6.py` (system prompt). `DifficultyConfig` holds display fields and `expectations` only; Expert stays defined but is unreachable while the Aim picker is live.
- **The Learn demands corpus has parity tests, and `hint` is not display-only.** `src/data/learn/__tests__/demandsParity.test.ts` fails on a stale `demandsManifest.ts` and (with `backend/` present, as in CI) on a `backend/data/learn/` that is not a byte copy — a mismatch is otherwise silent (`demandsResolved: false` switches L2 off). `Question.hint` feeds inference and avoidance, so learner-facing help goes in the display-only `Question.coachHint`, and Learn's focus chips in `Question.subTopic` (closed per-topic list in `src/data/learnSubTopics.ts`); both are checked by `src/data/learnBankLint.ts` via `npm run learn:check`, and neither is in `QuestionDemands`, so they never change `demandsVersion`. The corpus hash lives in `scripts/authoring/learnCorpusHash.ts`; don't import it from `buildDemandsManifest.ts`, which runs `main()` on import. **Batch 3b content rules:** every core-topic question has a `subTopic` (each key needs ≥ 5 questions or Batch 2 hides its chip), the eight priority topics (school, hobbies, family, holidays, home, future, food, environment) have a `coachHint` on every question, and no core question may be a bare yes/no (`learnBank.coverage.test.ts`; `reviewed` entries are exempt — their wording is the owner's to change). A demands entry whose `review.notes` is set is a model re-read: still `inferred`, never `reviewed`, and `learn:infer` refuses to overwrite it. Only a human flips `provenance` to `reviewed` (stamping `reviewedBy`/`reviewedAt`); don't do it from a session. Rewriting a question's text means re-tagging its demands in the same commit; a whole-question replacement (the five beyond-level ones) also rewrites `hint`, follow-ups, model answer and vocab so the old `hint` can't mislead inference or avoidance.
- **Coach-voice feedback is filtered once, at normalisation, and shows every fix (Learn Batches 4 and 6a, `learn-prompt-v6`).** The backend asks for every real error (most important first, still capped server-side by `FEEDBACK_DEPTH_ITEM_CAPS`), 2–4 quoted `strengths[]` (`best_moment` stays as the strongest, for older clients) and a second-person teacher voice whose `encouragement` is the opening line; `strengths[]` is why `FEEDBACK_CONTRACT_VERSION` is 3 (the client accepts ≥ 2). `apiClient.ts`'s `normalizeBackendFeedback` runs `domain/learn/feedback/filterCoachFeedback.ts` (grounding, identical correction, sound-alike only when the caller passes `inputMode: 'speech'` — Learn does, other screens don't — a strength or `strengths[]` item that quotes an error or ungrounded text, and an opening line that quotes nothing or fails the same rule), so the cards and belief evidence see the same errors; never add a display-only filter that leaves a dropped error counting in evidence, and never render a streamed section before that filter has run (while the feedback is generated nothing streamed is shown — the Predict card and a status line follow the real stream phase). The examiner minimum-quote rules are deliberately not used (they drop real one-word fixes). The coach view (`coachPoints.ts`, via the shared `FeedbackPointList`) is What you did well (every strength, else `best_moment`) → Fix these first (`FIRST_FIXES` = 2) → Also worth fixing (every other fix, deduplicated by quote across `issues[]` and grammar items) → Say it better → Go further (vocabulary, expansion ideas), but since Batch 6b it is spoken as the teacher's conversation (`features/feedback/teacher/`: `buildTeacherScript` arranges the already-filtered claims, `TeacherConversation` paces them — typing only the English talk, quotes whole, instant under reduced motion — and the Coach's first fixes are "Try it first" nudges checked by `fixMatch`, which only ever says yes, never "wrong"; the Examiner style gets the same conversation in the formal register through `LearnExaminerFeedback`). Nothing in that folder writes XP, evidence, sessions, storage or analytics; Predict answers are component state. `cefrLevel` stays a required A1–B2 enum on the wire (`feedbackSchema.ts`); display it only through `cefrLevelLabel`, never raw. `advanced_answer` is no longer requested but still ships as "" — keep the key.
- **Learn and feedback surfaces take colour from role tokens only (Learn Batch 5).** `src/screens/learn/__tests__/lightContrast.test.ts` bans raw 100–500 Tailwind colours for text/decoration, inline hex in `style=`, dark `bg-slate-*` panels/tracks and `text-white` on a violet button across `src/screens/learn/`, `src/features/{feedback,learn}/`, `Learn.tsx` and `MicroDrillModal.tsx`; use `text-ink*`, `text-{action,progress,reward,correction,info,streak}-text`, `bg-*-soft` + `border-hairline`, `bg-track`, `surface-recessed`, and `text-action-ink` on `bg-action`/gradient buttons (light mode turns `text-white` dark). The three pronunciation cards are allowlisted by name and `FeedbackExperience.tsx`'s pronunciation block is fenced by `lint:pronunciation-start/end` markers — keep the markers around it. `tokenContrast.test.ts` holds every `-text` token to AA in both themes (`--info-*` is the only token pair added). Severity colours live in `features/feedback/theme/severity.ts` (CSS variables / token classes, never hex); `scoreTone` (theme-aware, same 8/6 thresholds) is for Learn text, `scoreColor` stays for SVG strokes that need a literal colour. Tailwind opacity suffixes (`/70`) do not work on the `var()` token colours — pick a different token instead.
- **L1 evidence heuristics never enter the judge prompt until validated, even though they're computed.** `judgement/prompt.ts`'s `PROMPT_EVIDENCE_ALLOW_LIST` (currently `responseCountsByQuestion` and `topicConversationDurationByConversation` only) is the sole gate — `timeFrameAlignmentByQuestion`, `fillerDensityByQuestion`, and `rolePlayPartsByTask` are real, computed, envelope-snapshotted signals that must stay off that list until checked against real graded transcripts (see `docs/systems/assessment-engine.md`'s "What actually reaches the judge prompt"). Adding a signal to the allow-list is a scoring-behavior change, not a display change — it needs the Assessment-Engine change procedure, not a routine edit.
